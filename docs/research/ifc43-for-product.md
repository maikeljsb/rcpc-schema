# IFC 4.3 for the product module

*Research note, 2026-09-14, extended 2026-09-15 with an assessment of a colleague's parser (last section before Could not verify). Answers ten questions raised while preparing `SPEC-product` for `schema/product.yaml`: where `IfcBuiltElement` sits and what its subtypes are; what `PredefinedType` and the type/occurrence split mean for `ifc_type`; how one material string can be derived from `IfcRelAssociatesMaterial`; how a world-frame point is obtained from `ObjectPlacement` and what the project frame and unit are; which name attributes exist and whether they are optional; the exact definition of `IfcGloballyUniqueId`; which relations carry element to space, element to storey, and space to storey, and with what cardinality; how `IfcSpace`, `IfcBuildingStorey`, `IfcSite`, and `IfcExternalSpatialElement` are defined and which one is the join key for the outside; how openings, doors, and windows relate and where a clear width and height come from; and which base quantities exist for walls, slabs, beams, columns, and doors. Primary sources only: the buildingSMART IFC 4.3 HTML documentation under https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/ , which identifies itself on every page as "IFC 4.3.2.0 build 20260909 (IFC4X3_ADD2)". Method: each page was downloaded with curl on 2026-09-14 (the documentation server returns 403 to the WebFetch tool and 404 for the `.htm` suffix; the live pages end in `.html`), converted to text, and read in full for the sections cited. Every quotation below is verbatim from the named page; tables reproduce the page's attribute rows with the optionality marker as printed. Consequences for the module are stated after the evidence and are the author's, not IFC's. The module decisions listed in the brief (`docs/ideas/linkml-product-process-graph-schema.md`, section Product Side) are taken as fixed; this note only says what IFC offers each slot and where IFC does not offer what the slot wants.*

## Verdicts

**Q1. IfcBuiltElement and its subtypes.** The chain is IfcRoot > IfcObjectDefinition > IfcObject > IfcProduct > IfcElement > IfcBuiltElement, confirmed by the entity inheritance list on the IfcBuiltElement page. The page records "IFC4.3.0.0-CHANGE The entity has been renamed from IfcBuildingElement and made non abstract." It has thirty direct subtypes in 4.3 (table in the Q1 evidence): IfcBeam, IfcBearing, IfcBuildingElementProxy, IfcChimney, IfcColumn, IfcCourse, IfcCovering, IfcCurtainWall, IfcDeepFoundation, IfcDoor, IfcEarthworksElement, IfcFooting, IfcKerb, IfcMember, IfcMooringDevice, IfcNavigationElement, IfcPavement, IfcPlate, IfcRail, IfcRailing, IfcRamp, IfcRampFlight, IfcRoof, IfcShadingDevice, IfcSlab, IfcStair, IfcStairFlight, IfcTrackElement, IfcWall, IfcWindow. IfcWallStandardCase is not a direct subtype; it is a subtype of IfcWall and its page carries the banner "DEPRECATED This definition will be removed in a future major release of this standard". The IfcWall, IfcBeam, IfcDoor, IfcWindow, and IfcOpeningElement pages say that IfcWallElementedCase, IfcBeamStandardCase, IfcDoorStandardCase, IfcWindowStandardCase, and IfcOpeningStandardCase "has been deleted". IfcOpeningElement is not a built element: its chain is IfcElement > IfcFeatureElement > IfcFeatureElementSubtraction > IfcOpeningElement. IfcDoor and IfcWindow are direct subtypes of IfcBuiltElement. Consequence for the module: under the rule "only IfcBuiltElement subtypes become BuildingComponents", every door and window becomes a BuildingComponent, while the opening that hosts it does not; the spec must say whether a door is a BuildingComponent, the kind of an Opening, or both.

**Q2. `ifc_type` and PredefinedType.** PredefinedType is an optional per-entity enumeration attribute (IfcWall has `OPTIONAL IfcWallTypeEnum`, thirteen values). Its value is subordinate to the type object: the IfcWall page says "The PredefinedType shall only be used, if no IfcWallType is assigned, providing its own IfcWallType.PredefinedType", and on the type the attribute is mandatory (`IfcWallType.PredefinedType : IfcWallTypeEnum`, no OPTIONAL). USERDEFINED moves the label into `IfcObject.ObjectType` on the occurrence or `IfcElementType.ElementType` on the type. The entity name is stable because it is fixed by the schema and does not depend on the type object; it is coarse because it hides the predefined type (a PARAPET and a SOLIDWALL are both IfcWall) and because the docs advise instantiating IfcBuiltElement directly for kinds without a subtype. The occurrence/type split is IfcTypeObject (HasPropertySets) and IfcTypeProduct (RepresentationMaps), assigned by IfcRelDefinesByType, "a 1-to-N relationship". An occurrence inherits from its type the property sets (union of both, occurrence property of the same name overrides), the representation maps, the material association (except layer set and profile set usages, which are occurrence-only), and, per the Object Typing concept, "common naming and predefined type" and "common definition of a decomposition structure". Consequence: `ifc_type` as the bare entity name is well defined and needs no type lookup. If a finer kind is wanted later, the deterministic order is type PredefinedType, then occurrence PredefinedType, then ObjectType or ElementType for USERDEFINED.

**Q3. The material string.** `IfcRelAssociatesMaterial.RelatingMaterial : IfcMaterialSelect`, a select over IfcMaterialDefinition (IfcMaterial, IfcMaterialLayer, IfcMaterialLayerSet, IfcMaterialProfile, IfcMaterialProfileSet, IfcMaterialConstituent, IfcMaterialConstituentSet), IfcMaterialUsageDefinition (IfcMaterialLayerSetUsage, IfcMaterialProfileSetUsage), and IfcMaterialList, the last "deprecated from IFC4 onwards". Only `IfcMaterial.Name : IfcLabel` is mandatory; `IfcMaterialLayerSet.LayerSetName`, `IfcMaterialProfileSet.Name`, and `IfcMaterialConstituentSet.Name` are all OPTIONAL; the two usage entities have no name and point at their set through `ForLayerSet` and `ForProfileSet`; IfcMaterialList has no name, only `Materials`. A built element has at most one material association (where rule MaxOneMaterialAssociation on IfcBuiltElement). The material may sit on the type object instead of the occurrence, except usages: "If both, the element occurrence ... and the element type ... have an associated material, then the material associated to the element occurrence overrides the material associated to the element type." Proposed rule (author's, in Q3 evidence, step by step): take the occurrence association, else the type's; unwrap a usage to its set; if the target is an IfcMaterial, return its Name; if a set with a non-empty name, return that name; else if the set has exactly one member with a Material, return that member's `Material.Name`; else join the members' `Material.Name` values in list order with " / ", skipping members without a Material. It loses layer thickness and order semantics, profile geometry, constituent keywords and fractions, the air-gap flag, `IfcMaterial.Category`, and the difference between a named set and a single material.

**Q4. The point of an element.** `IfcProduct.ObjectPlacement` is OPTIONAL but "An object placement must be provided if a representation is present." IfcObjectPlacement is abstract with `PlacementRelTo : OPTIONAL IfcObjectPlacement` (moved to the supertype in 4.3) and three subtypes: IfcLocalPlacement (`RelativePlacement : IfcAxis2Placement`), IfcGridPlacement (virtual grid intersection), IfcLinearPlacement (distance along a curve, with an optional `CartesianPosition` fallback). A world-frame point is obtained by composing `RelativePlacement` transforms up the `PlacementRelTo` chain until it is absent: "If the PlacementRelTo is not given, then the IfcProduct is placed absolutely within the world coordinate system." The conventions are element relative to its container storey, opening relative to the voided element, door relative to the opening, site absolute. What the origin means: for a wall the x/y plane carries the profile and z is the extrusion direction, with the axis in the x/y plane parallel to x; for a slab likewise x/y profile and z extrusion; for beams and columns "the axis shall be defined along the z axis of the object coordinate system", offset from the profile by the cardinal point. None of the four pages says "the origin is at the base of the axis" in those words; that is a consequence of the conventions, not a quote. The project frame is `IfcContext.RepresentationContexts` (OPTIONAL) holding an IfcGeometricRepresentationContext with `WorldCoordinateSystem : IfcAxis2Placement` ("In most cases however it would be set to origin") and `TrueNorth : OPTIONAL IfcDirection` defaulting to the positive Y axis. The length unit is `IfcContext.UnitsInContext : OPTIONAL IfcUnitAssignment`, whose `Units` set holds the IfcNamedUnit with `UnitType = LENGTHUNIT`. `IfcSite.RefLatitude`, `RefLongitude`, `RefElevation` are OPTIONAL, WGS84, and locate "the point 0.,0.,0. of the LocalPlacement of IfcSite"; exact georeferencing is IfcMapConversion. Consequence: `target_location` should be defined as a point in the WorldCoordinateSystem of the project's Model context, in the project length unit, after resolving the full placement chain; the parser, not the schema, does the composing.

**Q5. Names.** `IfcRoot.Name : OPTIONAL IfcLabel`, `IfcRoot.Description : OPTIONAL IfcText`. `LongName : OPTIONAL IfcLabel` is defined on IfcSpatialElement and inherited by IfcSpace, IfcBuildingStorey, IfcSite, and IfcExternalSpatialElement; the IfcSpace page says "Name holds the unique name (or space number) from the plan" and "LongName holds the full name of the space". `IfcBuildingStorey.Elevation : OPTIONAL IfcLengthMeasure` carries "IFC4.3.0.0-DEPRECATION This attribute is deprecated and shall no longer be used. Within Pset_BuildingStoreyCommon use ElevationOfSSLRelative or ElevationOfFFLRelative instead." IfcSite adds RefLatitude, RefLongitude, RefElevation (all OPTIONAL) and two deprecated attributes, LandTitleNumber and SiteAddress. Only IfcProject requires a Name (where rule HasName). Consequence: `name` must be optional on all four module classes; `elevation` on Storey must be optional and its source is either the deprecated attribute, the property set, or the storey's own placement.

**Q6. IfcGloballyUniqueId.** "An IfcGloballyUniqueId is a Globally Unique Identifier (GUID) which is an auto-generated 128-bit number ... it is desirable to compress it". The alphabet is "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz_$", the result "is a fixed 22 character length string", "The first byte is encoded in the first two characters", "The remaining bytes are encoded in groups of 3, taking up 4 characters", "As a result, the first character must be either a 0, 1, 2, or 3." Formal: `TYPE IfcGloballyUniqueId = STRING(22) FIXED;`. Consequence: the `ifc_global_id` pattern should be `^[0-3][0-9A-Za-z_$]{21}$`.

**Q7. Spatial containment.** Element to spatial element: IfcRelContainedInSpatialStructure, `RelatedElements : SET [1:?] OF IfcProduct`, `RelatingStructure : IfcSpatialElement`; on the element side `ContainedInStructure : SET [0:1]`, and the page says "an element can only be contained within a single spatial structure element." Additional non-hierarchical links are IfcRelReferencedInSpatialStructure, "zero, one or several". Spatial decomposition is IfcRelAggregates, `RelatingObject` one, `RelatedObjects : SET [1:?]`, with `Decomposes : SET [0:1]` on the part, where rule WR41 ("All spatial structure elements shall be associated (using the IfcRelAggregates relationship) with another spatial structure element, or with IfcProject"), and the informal propositions that the tree is acyclic and that a site is never under a building, a building never under a storey, a storey never under a space. The Spatial Decomposition concept gives the order IfcSpace, IfcBuildingStorey, IfcBuilding, IfcSite, IfcProject with site, storey, and space optional levels. Space boundaries are IfcRelSpaceBoundary, `RelatingSpace : IfcSpaceBoundarySelect` (IfcSpace or IfcExternalSpatialElement), `RelatedBuildingElement : IfcElement` (mandatory since IFC4), "a one-to-one relationship, but allows each element ... to define many such relationships and each space to be defined by many such relationships"; subtypes IfcRelSpaceBoundary1stLevel (adds ParentBoundary) and IfcRelSpaceBoundary2ndLevel (adds CorrespondingBoundary, "Only 2nd level space boundaries of type A have corresponding boundaries"). So: element to space is containment (0..1, when the container is an IfcSpace) or boundary (0..many); element to storey is containment (0..1) or, when the element is contained in a space, that space's aggregation; space to storey is IfcRelAggregates (0..1 parent). Consequence: `contained_in` (one Storey, the IFC relation under its own name; renamed from `in_storey` on 2026-09-15) and `located_in` (one Space; the module's own name, since IFC has none for it) match IFC's cardinalities, but the containing level is project dependent ("A wall might be normally assigned to a storey"), so `located_in` from IFC alone will often be empty and is derived geometrically from the component's point, staying empty for walls and slabs by design.

**Q8. Space, storey, site, exterior.** IfcSpace: `CompositionType : OPTIONAL IfcElementCompositionEnum` (COMPLEX, ELEMENT, PARTIAL; default ELEMENT), `PredefinedType : OPTIONAL IfcSpaceTypeEnum` (BERTH, EXTERNAL, GFA, INTERNAL, PARKING, SPACE, USERDEFINED, NOTDEFINED; "IFC4.3.2.0-DEPRECATION INTERNAL and EXTERNAL are now deprecated. Use Pset_SpaceCommon.IsExternal instead."), `ElevationWithFlooring : OPTIONAL IfcLengthMeasure`. IfcBuildingStorey: Elevation as in Q5. IfcSite: as in Q4 and Q5. IfcExternalSpatialElement: "The external spatial element defines external regions at the building site", either "logically ... the air space around the building without having an own shape representation" or "physically ... the sloping ground around the building"; `PredefinedType : OPTIONAL IfcExternalSpatialElementTypeEnum` (EXTERNAL, EXTERNAL_EARTH, EXTERNAL_FIRE, EXTERNAL_WATER, USERDEFINED, NOTDEFINED); it has `BoundedBy` and is one of the two members of IfcSpaceBoundarySelect. IfcSite is not a member of that select and is defined as "a defined area of land". Verdict: IfcExternalSpatialElement is the correct IFC join key for the module's outside Space; IfcSite is the wrong entity. Two caveats: the element is optional in any file, and an exporter may instead model the exterior as an IfcSpace with `Pset_SpaceCommon.IsExternal = TRUE` ("A space is associated to a building storey (or in case of exterior spaces to a site)"). The module should accept either GlobalId in `ifc_global_id` of the outside Space and otherwise leave it absent.

**Q9. Openings, doors, windows.** IfcOpeningElement: `PredefinedType : OPTIONAL IfcOpeningElementTypeEnum` (OPENING, RECESS, USERDEFINED, NOTDEFINED); it "shall not participate in the containment relationship"; `VoidsElements : IfcRelVoidsElement FOR RelatedOpeningElement` is a mandatory single inverse ("The Opening Element can only be used to create a single void within a single Element"); `HasFillings : SET [0:?]`. IfcRelVoidsElement "is a one-to-one relationship" between `RelatingBuildingElement : IfcElement` and `RelatedOpeningElement : IfcFeatureElementSubtraction`. IfcRelFillsElement "is an one-to-one relationship" between `RelatingOpeningElement : IfcOpeningElement` and `RelatedBuildingElement : IfcElement`, with "View definitions or implementer agreements may restrict an opening to be filled by one filling element only." IfcDoor: `OverallHeight`, `OverallWidth : OPTIONAL IfcPositiveLengthMeasure`, each "reflects the ... Dimension of a bounding box, enclosing the body of the door opening" and "If omitted ... should be taken from the geometric representation of the IfcOpeningElement"; `PredefinedType : OPTIONAL IfcDoorTypeEnum` (BOOM_BARRIER, DOOR, GATE, TRAPDOOR, TURNSTILE, USERDEFINED, NOTDEFINED); `OperationType : OPTIONAL IfcDoorTypeOperationEnum` (25 values); `UserDefinedOperationType`. IfcWindow: same two measures, `PredefinedType : OPTIONAL IfcWindowTypeEnum` (LIGHTDOME, SKYLIGHT, WINDOW, USERDEFINED, NOTDEFINED), `PartitioningType : OPTIONAL IfcWindowTypePartitioningEnum` (11 values). Pset_DoorCommon and Pset_WindowCommon have no width or height property. Qto_DoorBaseQuantities and Qto_WindowBaseQuantities have Width, Height, Perimeter, Area, but Width is "Total outer width of the door lining" and Height "Total outer height of the door lining", so they are larger than the clear size. IfcDoorLiningProperties and IfcDoorPanelProperties still exist and hang off `IfcDoorType.HasPropertySets`. Best source for clear width and height: IFC has no attribute named clear; `OverallWidth` and `OverallHeight` are defined as the door opening size excluding the lining casing, which is the closest structural value; the Qto values are outer lining and should not be used. A door can exist without an opening: it can "be a "free standing" door, contained in an IfcSpatialElement such as an IfcBuildingStorey." Finding the two spaces from IFC alone: collect every IfcRelSpaceBoundary whose `RelatedBuildingElement` is the door (the door has `ProvidesBoundaries`); with 2nd level boundaries of type A the pair is linked explicitly by `CorrespondingBoundary`, and each door boundary is tied to the wall's boundary by `ParentBoundary`; going through the voided wall (IfcRelVoidsElement, then the wall's boundaries) yields all spaces the wall bounds, not the two at the door, so it needs geometry. This procedure is the author's reading of the attribute definitions, not a recipe printed in the docs.

**Q10. Dimension quantities.** Quantities attach by IfcRelDefinesByProperties ("an N-to-N relationship") whose `RelatingPropertyDefinition` is an IfcElementQuantity with `Name` equal to the template name, `MethodOfMeasurement = 'BaseQuantities'`, and `Quantities : SET [1:?] OF IfcPhysicalQuantity` of IfcQuantityLength (`LengthValue : IfcLengthMeasure`), IfcQuantityArea, IfcQuantityVolume, IfcQuantityWeight (`WeightValue : IfcMassMeasure`), each with an optional `Unit` that otherwise defaults to the project unit; every base quantity set here is `QTO_TYPEDRIVENOVERRIDE`, so it may sit on the type and be overridden at the occurrence. Names: Qto_WallBaseQuantities has Length, Width, Height, GrossFootPrintArea, NetFootPrintArea, GrossSideArea, NetSideArea, GrossVolume, NetVolume, GrossWeight, NetWeight. Qto_SlabBaseQuantities has Width (the thickness), Length, Depth, Perimeter, GrossArea, NetArea, GrossVolume, NetVolume, GrossWeight, NetWeight; no Height. Qto_BeamBaseQuantities and Qto_ColumnBaseQuantities have Length, CrossSectionArea, OuterSurfaceArea, GrossSurfaceArea, NetSurfaceArea, GrossVolume, NetVolume, GrossWeight, NetWeight; no Width or Height. Qto_DoorBaseQuantities has Width, Height, Perimeter, Area; no weight. A weight quantity exists for wall, slab, beam, and column, not for door or window. Consequence: the module's `length`, `width`, `height`, `weight` map cleanly only for walls; for slabs `height` has to be read from Width, for beams and columns width and height are not quantities at all (the IfcBeam page interprets `IfcRectangleProfileDef.XDim` as beam width and `YDim` as beam height), and doors have no weight. The spec should say the four slots are optional and the parser fills what the file has.

## Q1 evidence

Base URL for every entity page in this note: `https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/<EntityName>.html`.

### 1.1 Position in the hierarchy

https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcBuiltElement.html, section "Entity inheritance", lists the ancestors as a nested tree: IfcRoot, then IfcObjectDefinition, then IfcObject, then IfcProduct, then IfcElement, then IfcBuiltElement. The siblings of IfcBuiltElement under IfcElement are IfcCivilElement, IfcDistributionElement, IfcElementAssembly, IfcElementComponent, IfcFeatureElement, IfcFurnishingElement, IfcGeographicElement, IfcGeotechnicalElement, IfcTransportationDevice, IfcVirtualElement.

Semantic definition, same page: "The built element comprises all elements that are primarily part of the construction of a built facility, i.e., its structural and space separating system. Built elements are all physically existent and tangible things." And: "The IfcBuiltElement can be instantiated in the case when arbitrary built elements cannot be expressed by a subtype of IfcBuiltElement." History line: "HISTORY New entity in IFC1.0IFC4.3.0.0-CHANGE The entity has been renamed from IfcBuildingElement and made non abstract.NOTE It is advised not to use IfcBuildingElementProxy to represent an arbitrary built element, but to use a direct instantiation of IfcBuiltElement instead."

The ancestors' own definitions, one sentence each:

- IfcRoot (https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcRoot.html): "IfcRoot is the most abstract and root class for all entity definitions that are rooted in the kernel or in subsequent layers of the IFC specification."
- IfcObjectDefinition (https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcObjectDefinition.html): "An IfcObjectDefinition is the generalization of any semantically treated thing or process, either being a type or an occurrence."
- IfcObject (https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcObject.html): "An IfcObject is the generalization of any semantically treated thing or process. Objects are things as they appear - i.e. occurrences."
- IfcProduct (https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcProduct.html): "The IfcProduct is an abstract representation of any object that relates to a geometric or spatial context." Also relevant to the module's `permanence` slot: "Products can be designated for permanent use or temporary use, an example of the latter is formwork."
- IfcElement (https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcElement.html): "An element is a generalization of all components that make up a facility. Elements are physically existent objects, although they might be void elements, such as holes. Elements either remain permanently in the facility, or only temporarily, as formwork does."

The schema page https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/ifcsharedbldgelements/content.html says: "The shared building elements (IfcSharedBldgElements) define the subtypes of IfcBuiltElement, which is defined in the IfcProductExtension. Those subtypes are the major elements, which constitutes the architectural design of the building structure." Subtypes therefore live in several schemas (IfcSharedBldgElements for the building ones, IfcStructuralElementsDomain for footings and deep foundations, and the infrastructure domain schemas), which is why the section numbers in the table below differ.

### 3.3 Proposed deterministic rule (author's proposal)

Given an element E:

1. Let A be the IfcRelAssociatesMaterial in `E.HasAssociations` (at most one, MaxOneMaterialAssociation). If none, let T be `E.IsTypedBy[0].RelatingType` if present and let A be the IfcRelAssociatesMaterial in `T.HasAssociations`. If still none, `material` is absent. Basis: the override sentence in 3.1.
2. Let M be `A.RelatingMaterial`. If M is an IfcMaterialLayerSetUsage, replace M by `M.ForLayerSet`; if an IfcMaterialProfileSetUsage, by `M.ForProfileSet`. Basis: the usage entities carry no name and only position the set (3.2).
3. If M is an IfcMaterial, return `M.Name` (mandatory, so always present).
4. If M is a set (IfcMaterialLayerSet, IfcMaterialProfileSet, IfcMaterialConstituentSet) and its name attribute (`LayerSetName` or `Name`) is present and non-empty, return it.
5. Otherwise collect the members' materials in list order (`MaterialLayers[*].Material`, `MaterialProfiles[*].Material`, `MaterialConstituents[*].Material`, or `IfcMaterialList.Materials`), skipping members whose `Material` is absent. If exactly one remains, return its `Name`. If several, return their `Name` values joined with " / " in list order (constituent sets are SETs, so sort those by `Name` first to make the order deterministic). If none, `material` is absent.
6. A single IfcMaterialLayer, IfcMaterialProfile, or IfcMaterialConstituent used directly as RelatingMaterial (the select allows it) is treated as a one-member set.

What the rule loses: layer thicknesses, layer order and `LayerSetDirection`, offsets, and `TotalThickness` (derived on IfcMaterialLayerSet); profile geometry and cardinal point; constituent keywords that map to `IfcShapeAspect` names, and `Fraction`; the `IsVentilated` air-gap flag and layers with a `Name` but no `Material`; `IfcMaterial.Category` and any classification reference; and the distinction between "the set is called X" and "the material is X". The rule prefers a set name over the member names because a set name is what the authoring tool shows as the wall type's material, but a file with unnamed sets falls through to member names, so the same physical build-up can yield different strings across exporters. Where the module's `Method.applies_to` matches on material strings, that variability is the risk to record.

### 4.2 What the placement origin means for wall, slab, column, beam

Wall, https://standards.buildingsmart.org/IFC/DEV/IFC4_3/HTML/lexical/IfcWall.html, concept usage "Material Layer Set Usage": "The reference coordinate system is the local coordinate system established by the ObjectPlacement of the IfcWall. ### 9.5 Clear width and height, door without opening, the two spaces

Clear width and height: IFC 4.3 defines no attribute or base quantity called clear. The nearest is `IfcDoor.OverallWidth` and `OverallHeight`, which the page defines as the bounding box of "the door opening" and explicitly not "the total width of the door lining"; the Qto Width and Height are the outer lining and so larger. If OverallWidth or OverallHeight is absent the page's own fallback is the opening's geometry. A true clear passage (opening minus lining thickness, minus panel in the open position) is a geometric derivation the pages describe only through IfcDoorLiningProperties and IfcDoorPanelProperties on the type, and only "if the attribute IfcDoorType.ParameterTakesPrecedence is set TRUE". Consequence for the module: `clear_width` and `clear_height` should be documented as "OverallWidth and OverallHeight when present, else the opening's extent, else derived by the topology tool", and the SPEC should say which.

A door without an opening: yes; the first bullet on the IfcDoor page, "be a "free standing" door, contained in an IfcSpatialElement such as an IfcBuildingStorey." `FillsVoids` is `SET [0:1]`, so zero is allowed. A module Opening whose kind is door therefore cannot assume an IfcOpeningElement exists.

Finding the two spaces a door connects (author's procedure, from the attribute definitions in 7.3): collect every IfcRelSpaceBoundary whose `RelatedBuildingElement` is the door, using the door's `ProvidesBoundaries` inverse; each boundary names one `RelatingSpace` (an IfcSpace or IfcExternalSpatialElement); a door between two spaces has one boundary per side, and with IfcRelSpaceBoundary2ndLevel of type A the two are linked by `CorrespondingBoundary`. With 1st level boundaries, `ParentBoundary` ties each door boundary to the wall's boundary in the same space, which confirms which wall face it sits on but does not pair the two sides. Going through the wall instead (IfcRelFillsElement to the opening, IfcRelVoidsElement to the wall, then the wall's boundaries) yields every space the wall bounds, which for a long wall is more than two, so it needs the connection geometry to pick the two adjacent to the door. If the file has no space boundaries at all (they are optional, `BoundedBy : SET [0:?]`), the two spaces can only be found geometrically, which is what the brief already assigns to the topology tool.

## A colleague's parser: `ifc_utils/ifc_parser.py`

*Added 2026-09-15. Assessment of a parser a colleague wrote, placed at `C:/Users/go25qoh/Repos/ifc_utils/ifc_parser.py` (912 lines, one module). It turns an IFC into a per-storey room graph with ifcopenshell, shapely, and numpy, no topologicpy. Read in full; line numbers below refer to that file. Its output shape is only partly visible because it imports `make_record` and `room_features` from a sibling `schema` module that was not supplied (line 24).*

### What it confirms or adds for the schema

- **Same decomposition.** Levels with `levelName` and `elevation` (lines 598 to 602), rooms with `roomName` and `levelId` (lines 642 to 649), typed pair relations over room ids (lines 678 to 682). Storey, Space, `contained_in`, and `connects` are the same shape.
- **LongName over Name.** A room's name is `IfcSpace.LongName`, then `Name`, then a generated label (line 466). Confirms `long_name` on Space.
- **An outside node.** A synthetic `outdoor` room per level, created only when an exterior window is found (lines 703 to 714). The module's one outside Space with an optional `IfcExternalSpatialElement` join key covers the same need; the per-level variant is the fallback if outside access ever has to be per storey.
- **Relation kinds it needed.** `adjacency` through a wall, `connectivity` through a door, `visible_internal` and `exposed_external` through a window, `vertical` through a stair (lines 678 to 725). Adjacency without an opening is out of the module's scope (Phase 1, Q16). Vertical connectivity is new: `IfcStair` and `IfcStairFlight` are `IfcBuiltElement` subtypes (Q1), so a stair is a BuildingComponent, and it connects two Spaces on different storeys as a door connects two on one storey. Under `Opening is_a BuildingComponent` a stair fits the same slots; only the class name resists. Open decision: add `stair` to the kind enum, rename the subclass, or defer vertical connectivity.
- **Sill and head height.** Doors and windows carry `sillHeight` and `headHeight` in metres above the storey floor, read from the mesh (lines 348 to 350, 742 to 755). The module's `clear_height` is the difference; a sill height would let a query tell a window from a door without the kind enum. Not needed while `kind` exists.
- **Centroid versus representative point.** Rooms carry both (lines 651 to 659), because an L-shaped room's centroid can lie outside it. `target_location` as a centroid is fine for walls and slabs; if Space ever gets a point it should be an internal one.

### What it offers the generator

- **Unit handling.** `ifcopenshell.util.unit.calculate_unit_scale` (line 542) with `USE_WORLD_COORDS` (line 537) yields project-frame metres directly. This is what `docs/research/topologicpy-for-product.md` found missing in topologicpy, which only offers a manual scale factor.
- **Storey membership across schema versions.** Spaces hang off `ContainedInStructure` in IFC2x3 and IFC4 but off `IfcRelAggregates` in IFC4x3 (lines 149 to 157), and a stair landing reaches its storey only through the `Decomposes` chain (lines 227 to 247). Both helpers are reusable for `contained_in`.
- **Door geometry fallback.** When a door body is a swing arc rather than a solid, `create_shape` fails and the parser meshes the `IfcOpeningElement` the door fills instead (lines 278 to 297). This is the fallback Q9 names for clearances, with a real-world cause: Geometry Gym exports.
- **Connectivity by footprint overlap.** A door footprint buffered by 0.12 m that intersects two room footprints is a connection (lines 393 to 407); adjacency is buffered room outlines that intersect (lines 379 to 390). This answers the gap the topologicpy note found, where `IfcSpace` cells never touch across a wall: per storey, in 2D, with a tolerance, and without space boundaries in the file.
- **Vertical connectivity** by intersecting the union of stair footprints with rooms on consecutive storeys (lines 414 to 451).
- **Footprint from mesh.** The union of triangles lying on the lowest z plane, preserving L-shapes and bays that a convex hull would smooth away, with a convex-hull fallback (lines 160 to 185).
- **Refusals.** No storeys or no spaces raise a named error rather than an empty record (lines 556 to 577). Same posture as the module's tier 2.
- **Dependency footprint.** Space, Storey, door connections, and storey membership all come from ifcopenshell and shapely alone. topologicpy earns its place with the later 3D work: grids, occupancy, navigation.

### What it lacks for this project

- No GlobalIds. Rooms and levels are integer indices (lines 597, 605 to 607), so nothing joins back to the IFC.
- No door node. A door is an attribute of a relation (line 681), not a thing a task can install.
- No element-to-space containment, only element-to-storey (lines 131 to 136).
- Exterior doors are dropped, because a connection needs two rooms (lines 399 to 407); the module must attach them to the outside Space.
- No materials, no component attributes; walls, slabs, and stairs exist only as polygons for drawing (lines 734 to 763).

- **Precise wording of the IfcSharedBldgElements and IfcProductExtension schema pages on deprecation.** Both schema pages were fetched and their schema definitions are quoted in Q1, but they carry no deprecation list; all deprecation and deletion statements come from the individual entity and enumeration pages.
- **Unit examples.** IfcSIUnit's page was read for the attribute table and the gram note; no example instance (such as `IFCSIUNIT(*,.LENGTHUNIT.,.MILLI.,.METRE.)`) appears on the fetched pages, so the millimetre example in Q4 verdict is the author's, not a quotation.
