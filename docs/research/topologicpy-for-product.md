# topologicpy for the product module

*Research note, 2026-09-14, extended 2026-09-15 with what the topologicpy workshop under `C:/Users/go25qoh/Repos/topologicpy_workshop/Complete Notebooks/` shows on a real IFC (topologicpy 0.9.66 and 0.9.67, pythonocc backend; see the section From the workshop notebooks). Answers eight questions raised while planning `schema/product.yaml`: how topologicpy reads IFC and what it carries along; whether it builds Space cells; how it names a point for an element; how it tests containment; how it derives adjacency and apertures; whether it tells a shared wall from a door; what it knows about storeys; and what its graph output and exports look like. Primary sources only: the topologicpy source as installed from PyPI, version 0.9.69 (the `main` branch of https://github.com/wassimj/topologicpy carried `__version__ = '0.9.70'` on the day of writing; the latest GitHub release tag was v0.9.68 of 2026-09-07; PyPI shows 0.9.69 released 2026-09-13), the API docs at https://topologicpy.readthedocs.io/en/latest/, and probe scripts run against the installed package. Line numbers refer to the installed 0.9.69 files under `site-packages/topologicpy/`; the GitHub URLs point at the same files on `main`, where lines may have moved. The package was installed in isolation with `uv run --no-project --with topologicpy --with topologic_core`; the PyPI wheel of 0.9.69 depends on neither `topologic_core` nor `pythonocc-core` nor `ifcopenshell`, and without a kernel `Core.Backend()` raises `ImportError`. The `topologic_core` backend was used for every probe; the preferred `pythonocc` backend was not available. The user's pyenv site-packages leaked `ifcopenshell 0.8.5` into the isolated environment, which is why the one probe of `Graph.ByIFCPath` could run. There is no project IFC file; two minimal hand-written IFC4 files (`mini.ifc`, one wall and one space in millimetres with a site offset and a storey at +3000; `mini2.ifc`, two rooms, an interior wall with a door, an exterior wall with a door, IfcRelSpaceBoundary, IfcRelFillsElement, IfcRelVoidsElement, in metres) were authored in the session scratchpad `topologicpy-probe/` to exercise the readers. Everything else was probed on synthetic prisms. Every claim about behaviour cites the function and, where it was run, the probe output.*

## Verdicts

**Q1. Reading IFC.** Version 0.9.69 has two unrelated IFC paths. The geometry path is a pure-Python STEP parser in `IFC.py` (classes `IFCFastTopology` and `IFC`) that "intentionally avoids IfcOpenShell for geometry extraction" and is declared "a benchmark / experimental importer, not a complete IFC geometric kernel". It returns a list of topologies, one per `IfcProduct` that has a body representation, each carrying a `Dictionary`. `Topology.ByIFCFile` and `Topology.ByIFCPath` are the documented entry points but are broken in 0.9.69: they forward `scale` and `topologyType` to `IFC.TopologiesByPath`, whose signature has neither, so both raise `TypeError` (probe). The working entry point is `IFC.ModelByPath(path)` followed by `IFC.Topologies(model, includeTypes, excludeTypes, dictionaryMode, clean, epsilon, angTolerance, tolerance, circleSides, topologyType, scale, source, ontology, silent)`, or `IFCFastTopology.TopologiesByPath(...)`, which has the full parameter set. By default each product comes back as a `Cluster` of faces; `topologyType="Cell"` returns closed `Cell`s. The dictionary in `"basic"` mode carries `IFC_global_id`, `IFC_type`, `IFC_name`, `IFC_id`, `IFC_key` plus lower-case duplicates and a `label`; `"full"` mode adds every positional attribute as `IFC_arg_N`, named aliases (`IFC_overall_height`, `IFC_overall_width` for doors and windows), flattened property sets as `IFC_pset_<Pset>_<Property>`, quantities as `IFC_qto_...`, and materials as one comma-joined string under `IFC_materials`. Materials and property sets are absent in `"basic"` mode. Coordinates are project-frame: the `IfcLocalPlacement` chain is composed recursively down to the site, so a wall placed at x=500 in a storey at z=3000 on a site at (1000, 2000, 0) came back with `xmin 1500`, `zmin 3000` (probe). No unit is read: there is no handling of `IfcSIUnit` anywhere in the reader, so millimetre files stay in millimetres and the only conversion is the caller's `scale` factor (probe: `scale=0.001` gave metres). The geometry coverage matters for the schema: `IfcBooleanClippingResult` is "Approximation: keep first operand. This is fast but does not apply openings/cuts", profile voids are ignored, and `IfcOpeningElement` is skipped unless named in `includeTypes`. So walls come back without their door holes. The second path, `Graph.ByIFCFile` and `Graph.ByIFCPath`, requires `ifcopenshell` and builds a relationship graph (one vertex per `IfcRoot` entity, one edge per `IfcRel*` from its `Relating*` to each `Related*`), not a geometry model; in `importMode="geometry"` it reuses the pure-Python reader to move each vertex to the element's centroid or internal vertex and can store the BREP. The same entry point is what the workshop notebooks (section From the workshop notebooks) uses on an authoring-tool model: `IFC.ModelByPath`, then `IFC.Entities` once, then `IFC.TopologiesByEntities(entities, includeTypes, dictionaryMode)` per type, with `Topology.SelfMerge` closing each space into a Cell; on the IFC2x3 Duplex it imported 21 of 21 spaces, 57 of 57 walls, 21 of 21 slabs, 48 of 50 opening elements, and 2 of 4 stair entities. A write path also exists, `IFC.SemanticRelationshipsByGraph` and `IFC.Export`.

**Q2. Spaces.** Both. `IFC.Topologies(model, includeTypes=["IfcSpace"], topologyType="Cell")` builds a closed Cell from each `IfcSpace` body representation (probe: two rooms, volumes 35.1 and 35.1 model units cubed). `IFC.ThermalCellComplex(model, separatorTypes, margin, ...)` derives cells from the enclosing construction instead: each wall or slab becomes an oversized analytical plane through its centroid, the planes slice one enclosing box, and only the regions containing an `IfcSpace` interior vertex are kept and labelled with that space's dictionary. Its default `separatorTypes` match type names exactly, so `IfcWallStandardCase` walls are ignored until passed explicitly (probe: `None` with the default list, two cells with `["IfcWallStandardCase"]`), and it returns a Python list of Cells, not a `CellComplex`, because the assembling call is commented out in the source. Derived cells extend to the wall's centre plane and to the `margin` box on open sides, so they are not the room geometry. `IfcSpace` cells from authoring tools do not touch each other where a wall separates them, so `CellComplex.ByCells` assembles them but `Graph.ByTopology` finds no shared faces (probe: 2 vertices, 0 edges); that is why topologicpy's own IFC graphs derive adjacency from `IfcRelSpaceBoundary`, not from geometry. No function produces an "outside" Cell. `CellComplex.ExternalBoundary` returns the outer Shell. `IFC.AccessGraph` drops a door that touches only one space when `viaConnectingElements=False` ("found only 1 adjacent IfcSpace. Skipping.") and leaves it as a connector vertex with one edge when `True` (probe: exterior door B). The generator has to mint the outside Space itself and attach the single-space doors to it. One correction from the workshop notebooks (section From the workshop notebooks): the sentence about adjacency holds for `semanticConnections=True` only. With `spatialConnections=True`, `IFC.AdjacencyGraph` derives space relations from geometry by containment and proximity bands (`spatialRelationshipTypes`, `proximityValues`, `proximityLabels`), not by shared faces; on the Duplex that gave 252 edges over 21 spaces and 21 slab connectors, all of kind contains, near, medium, or far.

**Q3. Point of an element.** `Topology.Centroid(topology)` is an alias for `Topology.CenterOfMass`, which calls the kernel's centre of mass and returns a Vertex. `Topology.InternalVertex(topology, timeout, tolerance, silent)` "Returns a vertex guaranteed to be internal to the input topology"; `Cell.InternalVertex(cell, tolerance)` is the Cell-specific kernel call. `Topology.BoundingBox(topology, optimize=0, axes="xyz", mantissa, tolerance, silent)` returns a Cell whose dictionary has `xmin ymin zmin xmax ymax zmax width length height xrot yrot zrot`, merged with the input's own dictionary (probe). On the `topologic_core` backend it returned `None` for a zero-thickness vertical face; `Face.BoundingRectangle` handled that face and returned a Face with `width length xmin..zmax zrot`. For `target_location` the deterministic choice is `Topology.Centroid` of the imported product topology in the project frame (this is what `Graph.ByIFCFile` uses by default, `useInternalVertex=True` switches to `InternalVertex`); both return one Vertex whose coordinates `Vertex.Coordinates(v, mantissa=...)` gives as `[x, y, z]`.

**Q4. Containment.** `Vertex.IsInternal(vertex, topology, maxLeafSize, identify, tolerance, silent)` is the point test; for a Cell it reduces to `Cell.ContainmentStatus(cell, vertex, tolerance) == 0`, where "0 if the vertex is inside, 1 if it is on the boundary of, and 2 if it is outside", tested over the point and eight tolerance-cube corners. `Vertex.EnclosingCells(vertex, topology, exclusive=True, ...)` answers "which Cell contains this point": a BVH pre-filter over `Topology.Cells(topology)` then `IsInternal`; with `exclusive=True` it returns the first hit. Ties are not resolved: a point on the face shared by two cells returned `IsInternal` True for both cells and `EnclosingCells(exclusive=False)` returned both (probe), and `exclusive=True` returned whichever came first in the cell list. `Topology.Contains(A, B)` is a whole-topology test implemented as `Difference(B, A) is None`. Two consequences for `located_in` (the component-to-Space slot, named on 2026-09-15; `contained_in` is the storey relation): the generator should test with `exclusive=False` and treat two hits as a tie to resolve by rule; and a wall's centroid lies inside no `IfcSpace` cell at all (in `mini2.ifc` the wall occupies x 3.9..4.1 and the rooms stop at 3.9 and start at 4.1), so `located_in` for elements embedded in walls cannot come from point-in-cell on `IfcSpace` cells, and by the 2026-09-15 decision it stays empty: a wall is `contained_in` its Storey and `located_in` no Space. `IfcRelSpaceBoundary` (used by `IFC.AdjacencyGraph`, which returned the wall as the edge between the two rooms) or `IfcRelContainedInSpatialStructure` (storey) are the semantic alternatives, and `ThermalCellComplex` cells, which extend to the wall centre plane, are the geometric one.

**Q5. Adjacency and apertures.** `Graph.ByTopology(topology, direct=True, directApertures=False, viaSharedTopologies=False, viaSharedApertures=False, toExteriorTopologies=False, toExteriorApertures=False, toContents=False, toOutposts=False, idKey, outpostsKey, vertexCategoryKey="category", edgeCategoryKey="category", useInternalVertex=False, storeBREP=False, ontology=True, mantissa, tolerance, silent)` treats a CellComplex as cells (owners) and faces (boundaries). A face incident to two or more cells is "shared", a face incident to one cell is "exterior"; apertures are read off each face. Each option writes a distinct `relationship` value on the edge: `direct` gives one `Direct` edge between two cells for every shared face, aperture or not; `directApertures` gives one `Direct_Apertures` edge only where the shared face has an aperture, and copies the aperture's dictionary onto the edge; `viaSharedTopologies` adds a vertex at the shared face's centroid and `Via_Shared_Topologies` edges from each cell to it; `viaSharedApertures` adds a vertex per aperture on a shared face, offset by `tolerance * 100` from its centroid, with a `Via_Shared_Apertures` edge from each owning cell, so the aperture vertex has exactly two edges (probe: door vertex at (4.01, 1.51, 1.01) with edges from both rooms); `toExteriorTopologies` adds a vertex per exterior face with `To_Exterior_Topologies` edges; `toExteriorApertures` adds a vertex per aperture on an exterior face with one `To_Exterior_Apertures` edge from its single cell (probe: window vertex with one edge). That single-edge exterior aperture is how "outside" appears: there is no outside cell, only the dangling aperture vertex. Apertures are created with `Topology.AddApertures(topology, apertures, exclusive=False, subTopologyType=None, tolerance=0.001, silent)`, which sets `type: "Aperture"` on each aperture's dictionary, finds the host face by BVH clash plus `Vertex.IsInternal` of the aperture's internal vertex, and stores the aperture as content of that face; `Topology.Apertures(topology, subTopologyType)` reads them back by that `type` value. The legacy `Aperture.ByTopologyContext(topology, context)` and `Aperture.Topology(aperture)` exist but `AddApertures` does not use them. No IFC path calls `AddApertures` (zero occurrences in `IFC.py`), so doors and windows do not become apertures on import; the generator would have to build a Face per `IfcOpeningElement` and add it. Extents: `Face.BoundingRectangle(face)` returns a Face whose dictionary has `width`, `length`, `xmin..zmax` (probe on a vertical door face: `width 0.9, length 2.0, ymin 0.5, ymax 2.5, zmin 0.55, zmax 1.45`), so `clear_height = zmax - zmin` and `clear_width` is the horizontal extent; on an `IfcOpeningElement` imported as a Cell, `Topology.BoundingBox` gives `width 0.2, length 0.9, height 2.0` (probe), so `clear_height` is `height` and `clear_width` is the larger of `width` and `length` for an axis-aligned opening, or the extent along the wall for a rotated one. `IfcDoor.OverallHeight` and `OverallWidth` are positional arguments 8 and 9 and appear as `IFC_overall_height` and `IFC_overall_width` in `"full"` mode, but only on a topology, and a door without its own body representation is not imported; `IFC.ModelByPath(path).entities[step_id].args[8]` reads them directly. The workshop applies the same derivation to a Shell of faces, `TGraph.ByTopology(shell, direct=False, viaSharedTopologies=True)`: faces become vertices and shared edges become graph edges, which is the 2D floor-plan navigation graph one dimension below the CellComplex case (the workshop notebooks (section From the workshop notebooks).

**Q6. Shared faces without apertures.** Yes, the graph distinguishes them, by option and by the `relationship` key. `viaSharedTopologies` connects two cells through every shared face and knows nothing about apertures; `viaSharedApertures` and `directApertures` connect only through apertures; `direct` connects through any shared face. An edge's dictionary is the source topology's dictionary (the shared face's for `Via_Shared_Topologies` and `Direct`, the aperture's for the `*_Apertures` relationships, including its `name` and `type: Aperture`) plus `relationship`, `category`, `src`, `dst`, and with `ontology=True` also `ontology_class: top:Relationship`, `ontology_uri`, and `category` overwritten to `relationship`. Vertices carry their source dictionary plus `index` and, with `storeBREP=True`, `brep`, `brepType`, `brepTypeString`. The intended numeric category codes (0 direct, 1 shared topology, 2 shared aperture, 3 exterior topology, 4 exterior aperture, 5 contents, 6 outposts) are written by `_edge_dictionary` but were not visible in the probe because the ontology annotation overwrote `category`; the `relationship` string is the reliable discriminator. For the product module this means `connects` maps onto `Via_Shared_Apertures` plus `To_Exterior_Apertures` edges, and a wall between two rooms without a door produces no `connects` edge.

**Q7. Storeys and elevation.** Nothing groups topologies by level. `IfcBuildingStorey` is in the reader's product list but has no body representation, so it is never returned as a topology; its `Elevation` is positional argument 9 of the STEP record (probe: `['0Storey...', None, 'Level 1', None, None, ('REF', 51), None, None, 'ELEMENT', 3000.0]`) and the reader adds no alias for it, so it is read from `IFC.ModelByPath(path).entities[<id>].args[9]`. Storey membership comes from the relationship layer: `IFC.Triples(file)` (pure Python) yields `IfcBuildingStorey -- top:aggregates -> IfcSpace` from `IfcRelAggregates` and `IfcBuildingStorey -- bot:containsElement -> IfcWallStandardCase` from `IfcRelContainedInSpatialStructure` (probe), and `Graph.ByIFCFile` yields the same as edges typed `IfcRelAggregates` and `IfcRelContainedInSpatialStructure`. `IFC.AccessGraph` computes an `elevation` per space (Z of its internal vertex) but keeps it in an internal table, not on the vertex dictionary. Geometric helpers: `CellComplex.Decompose(cellComplex, tiltAngle=10, tolerance)` returns faces classified as `externalVerticalFaces`, `internalVerticalFaces`, `topHorizontalFaces`, `bottomHorizontalFaces`, `internalHorizontalFaces`, inclined and curved variants, and the apertures on each class (probe: 15 documented keys plus `curved`, `free`, and aggregate keys), so `bottomHorizontalFaces` are the floor faces whose Z is the storey level; `Topology.Slice(topologyA, topologyB)` cuts a CellComplex with a horizontal Face (probe: 4 cells from 2); `Graph.BOTGraph` takes `floorLevels` and otherwise computes them "from slab vertices when possible". A generator would read the storey id and elevation from the entities and assign each space by `IfcRelAggregates`, falling back to the centroid Z against the elevation list.

**Q8. Graph output.** A `Graph` vertex is a topologic Vertex with a Dictionary; a Graph edge is a topologic Edge with a Dictionary; `Graph.Vertices(graph, sortBy="index")` and `Graph.Edges(graph)` return them, and `Graph.MeshData(graph)` returns `{'vertices': [[x,y,z]...], 'edges': [[i,j]...], 'vertexDictionaries': [...], 'edgeDictionaries': [...]}` as plain Python. `Graph.ExportToJSON(graph, path, propertiesKey="properties", verticesKey="vertices", edgesKey="edges", vertexLabelKey="", edgeLabelKey="", xKey="x", yKey="y", zKey="z", indent=4, sortKeys=False, mantissa=6, overwrite=False)` writes `{"properties": {...}, "vertices": {"Vertex_0000": {<dictionary>, "x", "y", "z"}}, "edges": {"Edge_0": {<dictionary>, "source": "Vertex_0000", "target": "Vertex_0002", "src", "dst"}}}` (probe). `Graph.ExportToCSV` writes the PyTorch Geometric folder layout (`node_id`, `src_id`, `dst_id`, `label`, `feat`, train/val/test masks); `Graph.ExportToGEXF` writes GEXF; `Graph.BOTGraph` and `ExportToBOT` write RDF in the BOT ontology. `Neo4j.ByGraph(driver, graph, graphID, ...)` is a wrapper over `Neo4j.UpsertGraph(manager, graph, database, graphIDKey="graph_id", vertexIDKey="id", vertexLabelKey="label", ..., bidirectional=True, overwrite=False, ...)`, whose "canonical schema" is one `(:Graph {id, ...})` node, every vertex as `(:Vertex {uid, id, graph_id, label, ontology_class, category, uri, ifc_class, ifc_guid, x, y, z, props})` and every edge as `[:Edge {graph_id, ...}]`, with the remaining dictionary serialised into the `props` JSON string. That is a generic graph dump with fixed labels, not a projection of the model's classes, so it confirms the brief's decision to write our own LinkML-to-Neo4j component. `IFC.AccessGraph` and `IFC.AdjacencyGraph` return a `TGraph`, a pure-Python graph whose `TGraph.JSONData(tg)` is `{type, directed, allowSelfLoops, allowParallelEdges, dictionary, vertices: [{index, active, dictionary}], edges: [{index, src, dst, directed, active, dictionary}]}`; its space vertices carry the IFC dictionary plus `type: space, role: space`, its access edges carry `type: access, connector_id, connector_type, access_type: door, filling_id, filling_type: IfcDoor, vertical, relationship_source: semantic` (probe), and it has its own `ExportToJSON`, `ExportToCSV`, `ExportToGEXF`, and `ShortestPath`. The verified conversion from TGraph to Graph is missing: `TGraph.JSONDataGraphCompatible` emits vertices as a list, and `Graph.ByJSONDictionary` expects a dict keyed by id and raised `AttributeError` (probe). For the generator the cleanest consumption is `Graph.MeshData` or `TGraph.JSONData`: plain lists of coordinates, index pairs, and dictionaries. The missing conversion matters less than stated: `TGraph.ByTopology` performs the `Graph.ByTopology` derivation and returns a TGraph, and `TGraph.ShortestPath`, `ClosenessCentrality`, `BetweennessCentrality`, `MinimumSpanningTree`, `Density`, and `Diameter` cover the analytics on that type; `Plotly.DataByTGraph` and `Topology.Show` render it (the workshop notebooks (section From the workshop notebooks).

## Q1 evidence

### 1.1 Two readers and their dependencies

`IFC.py` header (https://github.com/wassimj/topologicpy/blob/main/src/topologicpy/IFC.py, lines 4-18 in 0.9.69):

> Pure-Python IFC topology importer for TopologicPy. This module intentionally avoids IfcOpenShell for geometry extraction. It parses IFC STEP text directly and converts supported IFC geometry constructs to TopologicPy topologies via Topology.ByGeometry. It is a benchmark / experimental importer, not a complete IFC geometric kernel. Supported constructs include common IFC2X3/IFC4 LOD100-LOD200 geometry: IfcExtrudedAreaSolid from arbitrary closed/void profiles, rectangles, circles; IfcShellBasedSurfaceModel / IfcFaceBasedSurfaceModel; IfcFacetedBrep / IfcClosedShell / IfcOpenShell / IfcFace / IfcPolyLoop; IfcBoundingBox; IfcPolyline / IfcIndexedPolyCurve; IfcMappedItem / IfcRepresentationMap; Approximate IfcBooleanResult / IfcBooleanClippingResult by first operand; IfcLocalPlacement and Axis2Placement transforms

The file defines `class IFCFastEntity` (line 43, a dataclass `id, type, args`), `class IFCModel` (57), `class IFCFastTopology` (430) and `class IFC` (3353). PyPI metadata for 0.9.69 lists `requires_dist` as numpy, scipy, pandas, shapely, plotly, lark, webcolors, nbformat, requests, packaging (probe: `importlib.metadata.distribution('topologicpy').requires`), so no kernel and no ifcopenshell. `Core.py` (https://github.com/wassimj/topologicpy/blob/main/src/topologicpy/Core.py) states "The preferred backend is ``PythonOCCBackend``. ### 1.3 What is returned

`IFC.Topologies` iterates `IFCFastTopology.ProductsByEntities(model.entities, includeTypes, excludeTypes)` (line 986): an entity is a product if its type is in `_PRODUCT_TYPES` (line 436, which includes `IFCSPACE`, `IFCDOOR`, `IFCWINDOW`, `IFCOPENINGELEMENT`, `IFCBUILDINGSTOREY`, `IFCSITE`, `IFCBUILDING`, `IFCPROJECT`, `IFCWALL`, `IFCWALLSTANDARDCASE`, `IFCSLAB`, ...) or passes `_is_product_like` (line 2423: type starts with `IFC`, not `IFCREL`, at least 7 arguments, argument 5 is a reference). Feature subtractions are excluded by default: "do not import subtraction features such as IfcOpeningElement as standalone visible products unless the caller explicitly requests them" (line 993). A product without mesh data is skipped (`if not mesh or not mesh.get("vertices"): skipped += 1; continue`, line 806), so storeys, sites, and doors without a body are not returned. The mesh becomes a topology through `Topology.ByGeometry(vertices, edges, faces, topologyType, tolerance, ontology, silent)` (Topology.py line 7644), whose docstring says of `topologyType`: "If set to None, a Cluster will be returned of vertices, edges, and/or faces"; for `"cell"` it tries `Cell.ByFaces` and falls back to `CellComplex.ByFaces` plus `ExternalBoundary` (line 7795).

Probe (`probe_ifc2.py`, `probe_ifcgraph.py`): default call returned `Cluster IfcWallStandardCase Wall A` and `Cluster IfcSpace Room 1`, six faces each; `IFC.Topologies(model, topologyType="Cell")` returned `('Cell', 'IfcWallStandardCase', 2240000000.0), ('Cell', 'IfcSpace', 33600000000.0)` (millimetre file, volumes in mm cubed); `Topology.ByGeometry(..., topologyType="Cell")` on the space mesh gave a Cell, `"Shell"` a Shell, `None` a Cluster.

### 1.4 Dictionary keys

`IFCFastTopology._entity_dictionary(entity, dictionaryMode, metadataCache, ontology, source, generatedBy)` (line 2812).
