# LinkML-Backed Product Process Graph Schema

*Idea brief, 2026-09-10. Output of an idea-refinement session; supersedes the reference schemas under `docs/reference-schemas/` as the statement of intent.*

## Problem Statement
How might we define a representation of robotic construction planning that humans can read and extend as a catalogue, that a loader can project onto the Product Process Graph without judgment calls, and that stands as a research contribution in its own right?

## Confirmed Intent
Confirmed 2026-09-10.

- **Outcome:** One LinkML model, four YAML files, that other teams can read and build against, that a Python component turns into a Neo4j Product Process Graph deterministically, and that is publishable as the representation.
- **User:** The author first, as the person writing the model and the graph. Then the other project teams who need a contract to code against without asking. Then the paper's reviewers.
- **Why now:** Other teams are blocked on the contract, and the paper is to be submitted by the end of 2026.
- **Success:** Another team validates their documents against the model without help; the conformance corpus proves the graph is deterministic; the paper is submitted with the model and its graph projection as the contribution.
- **Constraint:** Two, in order. The contract goes out before the generator exists, because that is what unblocks the other teams. Everything is publishable by December 2026, so the first increment cannot grow.
- **Out of scope:** See MVP Scope, Out.

## Recommended Direction
Author the domain model once, in LinkML YAML, and treat it as the single source of truth. Instance data, whether a hand-authored catalogue or components parsed from IFC, is validated directly against that model with `linkml.validator`. The Neo4j graph is a derived shape of the same model, produced by a Python LinkML-to-Neo4j component that owns all graph logic: it reads the schema to emit Neo4j constraints and reads validated data to write nodes and edges, on one shared rule table. The model itself stays neutral, with no graph vocabulary and no annotations, so SHACL, JSON Schema, and documentation can be generated from it for other consumers without contamination.

The component projects using LinkML's own metamodel and nothing else. Identified classes become node labels, `is_a` becomes stacked labels, classes marked `represents_relationship` become edges carrying their non-role slots as edge properties, reference slots become edges, primitive slots become properties, and identifier-less inlined objects are flattened to prefixed properties, keyed maps with the key as prefix, ordered lists with the position as prefix (2026-09-17). An identified object projects to a node and an edge whether it is written inline in the document or referenced by id: `inlined` shapes the document, never the graph. Node ids are authored by the data author and referenced, never minted by the component; edges carry no ids. Slot defaults declared with `ifabsent` are written by the component, because the validator and the generated JSON Schema ignore them; this is a metamodel rule, not a named-slot rule. One rule is keyed on a named slot rather than on the metamodel: a `RobotUnit` with `count` n yields n machine nodes with ids suffixed `_1` to `_n`, derived from the authored entry id and all linked to the same group nodes and capabilities. Recorded 2026-09-11 as the only such rule; a second one reopens the decision. The rule table is total over the constructs it accepts, and the component rejects any schema using a construct outside the table, with a reason. Two rejections are fixed now: a `represents_relationship` class that declares an identifier, and a multivalued class-ranged slot on such a class. That rejection is the guarantee: a schema it accepts projects deterministically, and data the validator accepts loads without judgment calls.

Wherever the reference schemas stored open-ended structure as data, the model instead uses a closed set of typed kinds, each a LinkML class. This applies to action parameters and, by the same reasoning, to preconditions.

The model is one schema split across four files joined by `imports`: `common.yaml` for shared types and kinds such as Position and Quantity, and for CapabilityType, since both the process side (`requires`) and the resource side (`offers`) point at it; `product.yaml` for BuildingComponent, Space, Storey, and Connector; `process.yaml` for PrimitiveTask, CompoundTask, Method, PrimitiveTaskInstance, CompoundTaskInstance, and the ParameterKind enum; `resource.yaml` for RobotUnit and its four Construction Robot Schema group classes. Product and resource import only common. Process imports common, product, and resource: methods match component materials, primitives take components, locations, and robots as parameters, and the `robot` binding on a PrimitiveTaskInstance, pointing at a machine node such as `sam100_2`, is the one edge that records allocation: the planner binds it, stage two may rewrite it. Nothing imports process. The assignment is stored once, on the task; "all tasks for this robot" is a query over the same edge, not a second slot. Amended 2026-09-17, see `docs/research/pddl-for-process.md`. The split is for readability. Validator, generator, and documentation see a single model.

## Design Inspirations
The model borrows structure from three sources. "Inspired by" means adapted: for each, a borrowed/adapted/dropped table records the lineage under one house naming style.

- **Product side: IFC.** Borrow the occurrence/type split (`IfcWall` versus `IfcWallType`), which mirrors the catalogue/instance split across the whole model, the GlobalId as the join key for components that come from IFC, and the property-set idea for planning-relevant attributes. Do not copy geometry or the full element hierarchy: IFC remains owner of element detail; the graph holds the join key and what planning needs. IFC's own process classes are a cross-check, not a source. Method applicability matches the material string IFC already carries on the component; no taxonomy is built.
- **Process side: HDDL and HDDL 2.1.** Borrow the three concepts below and the subtask network with ordering. Method applicability is a constraint on the component parameter, as HDDL constrains method parameters, not a state-based method precondition, which the HDDL authors call "somewhat problematic" because it is usually search advice. In the model it is a list of accepted material strings on the method's component parameter. Capability requirement is an ordinary primitive-task precondition. From HDDL 2.1 (Pellier et al., 2023) borrow a duration on each primitive task. Ordering is between whole subtasks, HDDL's `:ordering`; HDDL 2.1's ordering over start and end events is a proposal its own Transport benchmark does not use and is not taken (2026-09-17). Leave out its "at e φ" constraints. Producing runnable HDDL from the graph is outside the model, but the mapping should be a straight walk.
- **Resource side: the Construction Robot Schema** from "A Planning Schema of On-Site Construction Robot Operation." Borrow its physical, operational, safety, and activity attribute groups as four classes, `PhysicalProperty`, `OperationalRequirement`, `Safety`, `Activity`, each held by `RobotUnit`. Adapt units to the model's quantity kind, split type from unit, and relocate attributes the process side already owns, such as capabilities, so nothing is declared twice.

## Domain Structure: HDDL
The process side follows HDDL (Höller et al., AAAI 2020) and uses its words. Three catalogue concepts, no more.

| Class | HDDL | Carries | Example |
|---|---|---|---|
| `PrimitiveTask` | Primitive task, also "action" | Name; parameters, each of kind `component`, `location`, or `robot`; capability requirements as its precondition; duration. Effects deferred, see Preconditions as Relation Kinds. | `MoveTo`, `Attach`, `Detach` |
| `CompoundTask` | Compound task, also "abstract task" | Name and typed parameters only. No body, no state change. | `ConstructComponent(component)`, `Transport(component)` |
| `Method` | Decomposition method | Its `task`, the compound task it decomposes; `parameters`, every variable its subtasks use, the component one carrying the material strings it applies to; `subtasks`, an ordered list of entries, each a task name followed by its parameter sequence, `[r, l0, from]`; `ordering`, pairs of positions in that list, a partial order | `m-prefab` decomposes `ConstructComponent` for components whose material is in its list |

A ConstructionMethod is simply a `Method` whose task is `ConstructComponent`. Several methods may refine the same compound task; choosing among them is the planner's job. The reference `TransportComponent` splits into a `CompoundTask` `Transport` and one `Method` refining it into `MoveTo, Attach, MoveTo, Detach`; a second transport method can be added later without touching anything else.

The catalogue is the HDDL domain. The product and resource documents are the problem: components, spaces, and machines are its objects, and `located_in`, `offers`, and `status` are its initial state. The parentless `CompoundTaskInstance`s are the initial task network, and the tree below them is the decomposition HDDL calls a solution. Writing the HDDL files is a straight walk over these documents; `docs/research/pddl-for-process.md`, Appendix B, exports one method and solves it.

On the instance side, each record is a `PrimitiveTaskInstance` or a `CompoundTaskInstance`, pointing at its catalogue task with every parameter bound to an object id. The compound also points at the method chosen and binds that method's variables once; its children inherit those bindings and their order from the method, as HDDL's Definition 5 derives them, so no copy is written. Ordering is authored only between the parentless compounds, HDDL's initial task network. There is no separate Task-as-plan-unit and no catalogue-side compound action. Decided 2026-09-17.

The graph path this yields, and the picture the paper should open with: BuildingComponent, matched by material, to the Method that applies, whose `subtasks` point at PrimitiveTasks, one edge per subtask carrying its position, each of which `requires` CapabilityTypes that a RobotUnit's Activity `offers`. Product, process, and resource in one query.

## Preconditions as Relation Kinds
Preconditions and effects are not a formula language. They are a closed set of kinds, each projecting to a graph pattern a query can match. The graph gives a planner typed facts; the planner reasons.

| Kind | Pattern | Enables | Slice |
|---|---|---|---|
| Applies to product | Method lists accepted material strings; a BuildingComponent matches if its material is among them | Method selection, the Product-to-Process link | First |
| Requires capability | PrimitiveTask requires CapabilityType; the RobotUnit's Activity offers it | Type-level task allocation | First |
| Ordering | Subtask before subtask, pairs of list positions on the method, a partial order; the same between the parentless compounds of a ground document | Sequencing | First |
| Acts on component | A parameter of kind `component`, bound to a BuildingComponent on the instance | Product-process join | First, as a parameter kind |
| At location | A parameter of kind `location`, bound to a Space on the instance | Where a step happens | First, as a parameter kind |
| Performed by | A parameter of kind `robot`, bound to a machine node on the instance; the planner binds it through `requires` and `offers`, stage two may rewrite it within the entry | Allocation, both stages | First, as a parameter kind |
| Component state | Task requires or produces a component state such as placed, fixed, inspected. This is where effects enter the model. | Real preconditions and effects on the product | Later |
| Resource availability | The machine node's `status` is `idle` during the task's duration | Scheduling | Later |
| Capacity | A fact on the component compared against a fact of the machine's `PhysicalProperty`, such as component weight against load capacity; PDDL's numeric comparison, not a parameter | Rejecting robots that cannot do the task, before stage two | Later |
| Located in | BuildingComponent is located in a Space, resolved from its point; its Storey is `contained_in`, IFC's own containment relation | Locating work, resolving a Position to a Space | First in the contract; instances derived later |
| Connects | Connector connects exactly two Spaces, the exterior of each storey being a Space, carrying clear width and height | Reachability, door-fit checks, path finding | First in the contract; instances derived later |
| Derived from | A derived BuildingComponent points at the IFC-sourced BuildingComponent it was generated from | Product lineage, wall-to-bricks | First |

## Two-Stage Allocation and Execution
Allocation happens twice, at different granularity, with different data, and the model must serve both without confusing them.

**Planning allocates to an entry.** HDDL-level planning uses only the `requires` / `offers` pattern: this primitive needs lift and align, and every machine of entry SAM100 offers both, so any of them can do it. The planner sees one object per machine, `sam100_1` to `sam100_n`, generated from `count`, and the machines of one entry are interchangeable, so "one of the five" is what a plan says. There is no `RobotType`: the entry is the type. Amended 2026-09-11, see `robot-entry-as-type.md`.

**Orchestration allocates to a machine.** At execution time a separate step, using multi-robot task allocation algorithms rather than HDDL, refines the plan to a specific machine: "of the five SAM100s, `sam100_2` is most suitable," judged on the group attributes, current position, battery, and `status`. It writes its choice by rewriting the `robot` binding on the `PrimitiveTaskInstance` with another machine of the same entry (2026-09-17). This is where the Construction Robot Schema's quantitative attributes earn their place. Every attribute lives in one of the four group classes, shared by the machines of one entry; `status` lives on the machine node and is written by orchestration; position and battery are runtime state outside the model.

**Execution is a behaviour tree.** The allocated, instantiated task network is mapped to BT.CPP XML: a compound becomes a control node, Sequence for totally ordered subtasks, Parallel where the ordering allows, and a primitive becomes an action leaf whose name and filled parameters the tree can dispatch to the assigned unit. The mapping is a downstream consumer, out of MVP scope, but it imposes three requirements on the model now: every primitive must be addressable as a BT leaf, ordering must be expressible as control-node nesting, and the `PrimitiveTaskInstance` records its machine in its `robot` binding.

Neither stage-two allocation nor the BT mapping is native to HDDL. Both are their own algorithms and their own specs. They are in this brief because they fix what the resource model has to carry and where the entry/machine boundary falls.

## Product Side
The Product contract is part of the first slice. What comes later is only the tooling that fills it.

**BuildingComponent.** Every component carries two orthogonal distinctions as required slots:

- `permanence`: `permanent` or `temporary`. Reinforcement is permanent; formwork is temporary.
- `source`: `ifc`, parsed directly from the model, or `derived`, added by an external algorithm. Bricks are the standard example: usually absent from the IFC model, yet needed as components. The producing algorithm is not recorded; a derived component names the component it came from, nothing more. Amended 2026-09-15.

Every record's `id` is an IFC GlobalId in the 22-character form: the entity's own when `source` is `ifc`, minted deterministically in the same format by the derivation when `source` is `derived`, so the id survives a re-export of the model and a derived component can later be written back into the IFC. An IFC-sourced component carries `ifc_type`; a derived component carries `derived_from`, an edge to the IFC-sourced component it was generated from, so the wall-to-bricks relationship is in the graph. Both conditional requirements are LinkML class rules that the validator and the generated JSON Schema enforce, so they are tier 1 checks (probed on LinkML 1.11.1, 2026-09-15). A part of an IFC element assembly, such as a stair flight, is a component of its own and carries `part_of` naming the assembly. `ifc_type` carries the bare IFC entity name, such as `IfcWall`; only `IfcBuiltElement` subtypes become components, with the one exception named under Spatial topology. `material` is a single IFC material string and optional: a component without one cannot be matched to a method and is a work item for the person resolving the model, found by a tier 3 query, not a shape error, because the front end loads the parsed model first and flags such components for a human. `name` carries the IFC Name. `BuildingComponent` is subclassed by kind only, never by source or permanence; see Decisions Taken by Default. Formwork is often both temporary and derived; the two slots are independent.

**Locations.** Every component carries `target_location`, required: the centroid of its body in the IFC project frame, where the design puts it and what a placement task binds to. `supply_location`, where it is delivered or staged, and `current_location`, where it is now, are optional. Current location is written by execution and is the model's second runtime exception after `status`; see Not Doing. Decided 2026-09-14 in Phase 1 of SPEC-product.

**Spatial topology.** The Product side carries a light topological graph. `Space` nodes with `name`, `long_name`, and `source`: parsed from `IfcSpace`, or derived, rooms cut from wall footprints per storey when the file has no spaces, and one exterior Space per storey so that an exterior door and a roof stair each have two ends without every exterior passage meeting at one node; the ground storey's exterior takes the `IfcExternalSpatialElement` GlobalId when the file has one. `Storey` nodes identified by their GlobalId with `name`, `long_name`, and `elevation`. `Connector`, a subclass of BuildingComponent and the model's one `is_a`, for what a robot passes through: a door, an unfilled opening, or a stair is one node that carries the component slots and, in addition, `connects` to exactly two Spaces, `clear_width`, `clear_height`, and a `kind` (door, void, stair); a window is a plain component, not a passage; a stair connects two Spaces on different storeys, its `clear_width` is the flight width and its `clear_height` the headroom, read from geometry because IFC carries neither as an attribute, so both are optional for kind stair and required for the other kinds; an `IfcOpeningElement` with no filling becomes a Connector of kind void, the one exception to the rule that only built elements become components. `located_in` edges from a BuildingComponent to the Space its point lies in, empty for walls and slabs. `contained_in` edges from a BuildingComponent or a Space to its Storey, the IFC containment relation under its own name. These classes and slots are in the contract from the first slice. Their instances are derived, not authored, and that derivation is a later slice. What the research fixed about it (2026-09-15, `docs/research/ifc43-for-product.md` and `docs/research/topologicpy-for-product.md`): Space cells never touch across a wall, so connections do not come from space geometry; they come from `IfcRelSpaceBoundary` when the file has it and otherwise from door footprints overlapping room footprints per storey, which ifcopenshell and shapely do without topologicpy. Clearances come from the door's OverallWidth and OverallHeight, with the opening's geometry as fallback. topologicpy reads a real model's spaces, walls, slabs, and openings, but does not attach doors as apertures, mint an outside cell, group by storey, or read units, so it serves the later 3D work rather than the first derivation. IFC's spatial structure (`IfcSpace`, `IfcBuildingStorey`, `IfcOpeningElement`, `IfcDoor`, `IfcExternalSpatialElement`, spatial containment) is the source; the Building Topology Ontology is a cheap `exact_mappings` target later, nothing more.

The two questions the topology answers are queries, not model logic, and belong to stage two: "does this robot fit through that door" compares a machine's `PhysicalProperty` dimensions with a `Connector`'s clearance; "how to move from A to B" is a shortest path over Space adjacency.

`Position` must be a coordinate in the same site frame the IFC parse produces, so a position can be resolved to its Space at parse time.

## Error Tiers
The guarantee "follow the schema and you get a graph, don't and you get an error" holds only if each kind of error has one named owner. There are three, ordered by how much context is needed to detect them.

| Tier | Question | Context needed | Owner | Example |
|---|---|---|---|---|
| 1. Shape | Is this document well formed against the model? | The document and the schema | `linkml.validator` | `requires` is a string, not a list |
| 2. Key | Does every key point at something that exists, and does the value fit its declared kind? | All documents, parsed together | The generator, at parse time, before any write | A method's task is `Weld`; no such compound task exists. A subtask lists too few parameters for its task, or one that is neither a method parameter nor an object. A `robot` binding names a machine id the entry's `count` does not yield |
| 3. Domain rule | Is the assembled structure legal? | The whole graph | Post-load checks: Cypher queries that must return zero rows, in the same transaction so a violation rolls back | Ordering forms a cycle. A component whose material is in no method's list |

Tier 2 is a parse check. `linkml.validator` checks that a key has the right shape, never that its target exists; bundling documents into one run does not change that (verified against the validator source, see `docs/research/linkml-neo4j-and-metamodel.md`). So the generator parses all documents, indexes every identifier, and flags a key with no target as an error and a definition nothing points at as a warning. It needs that index anyway to create edges. Tier 3 rules are not expressible in LinkML and are documented and tested as part of the artifact rather than folded into the schema and lost.

## Key Assumptions to Validate
- [ ] **LinkML's metamodel alone disambiguates the projection.** Test: write the rule table over `identifier`, `inlined`, `represents_relationship`, `relational_role`, `is_a`, `multivalued`, `range`, then walk every class through it. Any class needing a case outside the table is a finding.
- [x] **A closed set of parameter kinds covers every primitive in the reference `actions.json`.** Verified 2026-09-10 with `position` and `component_reference` (`docs/research/parameter-kinds-mapping.md`); reopened and re-answered 2026-09-17 from PDDL's own rule that parameters range over objects and numbers are functions, not parameters (`docs/research/pddl-for-process.md`, 2.2): the kinds are `component`, `location`, and `robot`. Positions are slots on the component, quantities are facts on the component or the machine. Duration is a slot on `PrimitiveTask`, not a parameter kind.
- [ ] **Material-list applicability plus capability matching are enough for method selection and type-level allocation.** Test: migrate the reference catalogue, write both queries, and check each returns what you'd choose by hand. Where it doesn't, name the missing kind rather than adding logic to the query.
- [x] **The type/unit split in the resource model is clean.** Answered 2026-09-11, see `robot-entry-as-type.md`: there is no type. Every Construction Robot Schema attribute has one home in one of four group classes held by `RobotUnit`, and `status` is the only per-machine fact in the model.
- [ ] **The three inspirations share one house style without losing lineage.** Test: write the borrowed/adapted/dropped table for each before writing classes.
- [ ] **`linkml.validator` catches the shape tier without a hand-maintained JSON Schema.** Its default plugin generates one internally, which is fine. Test: validate the migrated catalogue directly.
- [ ] **Topologicpy can read the project's actual IFC files and derive Space adjacency and Connector clearances from them.** Partly answered 2026-09-15, see `docs/research/topologicpy-for-product.md`: it reads spaces, walls, slabs, and most openings from an authoring-tool model (the Duplex), but Space adjacency does not come from its space geometry, doors do not become apertures on import, and units are not read. Connections are derived from space boundaries or door footprints and clearances from door attributes, so the topology is derived, not authored, and one ifcopenshell parse can feed both components and topology; topologicpy is for the later 3D work. Still to do: run on the project's own models and check against the drawings.
- [ ] **Each error tier has exactly one owner that catches its tier.** Test: one deliberately broken document per tier, each failing where the table says and nowhere else.
- [x] **No existing LinkML-to-Neo4j backend already does this well.** Verified 2026-09-10, see `docs/research/linkml-neo4j-and-metamodel.md`: no official generator exists; linkml-store's adapter and KGX project from data-row conventions, not from the schema. Write our own on `SchemaView`; borrow KGX's batching and constraint pattern. `represents_relationship` and `relational_role` exist but are marked "testing" and no shipped generator consumes `relational_role`, so this would be its first consumer.

## MVP Scope
Sequenced by the constraint. **Step 1, the contract:** the four YAML files, the documentation LinkML generates from them, the JSON Schema for the viewer, and the migrated reference catalogue as example instance documents, shipped to the other teams. The examples double as the first conformance corpus in step 2. **Step 2, the proof:** the generator, the tier 2 and tier 3 checks, and the conformance corpus. Same scope; the contract lands before the code because the dependency needs it.

**In.** The LinkML model for the catalogue: `PrimitiveTask` with parameters of kind `component`, `location`, or `robot`, a duration, and `requires` to `CapabilityType`; `CompoundTask`; `Method` with its task, parameters, `applies_to` material strings on the component parameter, `subtasks`, and `ordering`; `CapabilityType`; `RobotUnit` with `count`, `status`, and the four Construction Robot Schema group classes, `offers` on Activity. The borrowed/adapted/dropped table per inspiration. The Python component with its rule table, emitting constraints from the schema and writes from data, refusing unprojectable schemas with a reason, performing tier 2 checks before writing. Tier 3 checks as a documented query set. A conformance corpus: example documents paired with the exact graph each must produce, plus one broken document per tier; the migrated reference catalogue is the first corpus. The Product contract: `BuildingComponent` identified by its GlobalId, with `ifc_type`, `permanence`, `source`, optional `material`, `target_location`, `derived_from`, `part_of`, `located_in`, and `contained_in`; `Space` with `source`; `Storey`; `Connector` (door, void, stair) as a subclass with clearances and `connects`. On the instance side, one component with its `CompoundTaskInstance` and `PrimitiveTaskInstance`s, to prove the full path BuildingComponent to Method to PrimitiveTask to CapabilityType to RobotUnit as a single query, with the `robot` parameter bound on each `PrimitiveTaskInstance`, so stage two has somewhere to write. Generated JSON Schema as a secondary output for the viewer.

**Out.** Plan, Run, ExecutionRecord, the IFC parser, and the derivation of Spaces, Storeys, and Connectors from IFC. The classes are in; the tools that populate them are not. HDDL export. Stage-two allocation algorithms. BT.CPP generation. SHACL generation and RDF loading. Formal ontology alignment. Component-state and resource-availability kinds, and with them effects. Any graph vocabulary in the LinkML files.

## Not Doing (and Why)
- **Hand-authored JSON Schema with a prose mapping.** It's what the reference schemas are, and the guarantee lives in the loader author's head.
- **Graph annotations in the LinkML model.** The metamodel already carries the needed distinctions; annotations would leak Neo4j into a model that also serves SHACL and documentation.
- **Guessing in the generator.** Unprojectable constructs are rejected with a reason. A permissive generator produces a graph nobody can explain. The `count` rule is deterministic and recorded, not a guess.
- **A Task class as plan unit, or a catalogue-side compound action.** HDDL's three concepts cover it. `TransportComponent` becomes a compound task plus a method.
- **State-based method preconditions.** HDDL's authors flag them as search advice. Applicability is a list of accepted material strings on the method.
- **A precondition language.** Preconditions are a closed set of relation kinds that project to patterns. Formulae belong to the planner.
- **Runtime state in the model.** Position, battery, and wear are read from the robot at run time and stay outside the model. Two exceptions: `status` on the machine node, written by orchestration, and `current_location` on the BuildingComponent, written by execution. Amended 2026-09-11 and 2026-09-15.
- **Copying any inspiration wholesale.** Borrow structure, record the adaptation.
- **Ontology alignment up front.** `exact_mappings` can be added later at near-zero cost.
- **Subclassing `BuildingComponent` by source or permanence.** Provenance and lifetime are slots. Subclasses are for kinds, added on demand.
- **Full IFC-to-graph round trip in the first slice.** It multiplies entity count before the rule table is proven.

## Decisions Taken by Default
Accepted as working defaults on 2026-09-10; revisit if they bite.
- `RobotUnit` and the `robot` parameter binding are in the first slice so stage two has a target. The target is a machine node generated from `count`. Amended 2026-09-11 and 2026-09-17.
- Ordering is between whole subtasks, HDDL's `:ordering`, written as pairs of list positions on the method. The earlier default, ordering over start and end events from the start, is reversed: both HDDL grammars order whole tasks, and HDDL 2.1's event-level ordering is a proposal its own Transport benchmark does not use. Reversed 2026-09-17.
- The product class is `BuildingComponent`, the project's term, not `Element`. Decided 2026-09-10.
- The generator emits Cypher plus parameter JSON; a thin `apply` command loads them through the driver. Unit tests compare generated Cypher against the conformance corpus with no database running; one integration test applies it and checks the graph. Decided 2026-09-10.
- One coordinate frame, the IFC project frame, for every Position in the model. No frame slot. Transforming a robot's own frame into it is orchestration's job, outside the model. Decided 2026-09-10.
- The rule table lives in `PROJECTION.md` and the tier 3 query set in `CHECKS.md`, both beside the generator; the BT mapping requirements are a section in the model documentation generated from class descriptions. The repo is the published artifact. Decided 2026-09-10.
- `offers` is a flat set of capability types. Type-level allocation is set containment. The known gap, an entry that offers `lift` but whose load capacity is below the component weight, is recorded as the Capacity relation kind, Later. Decided 2026-09-10.
- Parameter declarations and the bindings on ground tasks are maps keyed by parameter name, using LinkML's `key` slot on the small class. The generator flattens a keyed inlined map to properties prefixed by the key (`target_kind`, `target_x`), and a reference-valued entry becomes an edge carrying the key. An unkeyed multivalued inlined object is an ordered list, and its position, counted from 1, is its key. No child nodes. A method's `subtasks` is such a list: each entry names its task and lists its parameters in the task's order, a plain list of strings as HDDL writes `(move ?r ?l0 ?from)`, so the graph has one edge from the method to the task per entry, carrying the position, and the same task used twice is two parallel edges; `ordering` is a list of position pairs, `[[1, 2], [2, 3], [3, 4]]`, an array slot of two dimensions, the one LinkML construct that admits it. The validator accepts any array there (probed 2026-09-17), so that each pair names two existing positions is a tier 2 check, and the rule table gains a case for a two-dimensional array of primitives, which a Neo4j property cannot hold nested. Subtasks are not nodes. The shape is `rep_b.yaml` in `docs/research/pddl-for-process.md`, Appendix B, validated against a LinkML schema of that shape and exported to HDDL there. Decided 2026-09-10; subtasks reversed 2026-09-17 after the experiment in `docs/research/pddl-for-process.md`, Appendix B, showed planning indifferent to the choice.
- Method applicability is `applies_to`, a list of exact material strings as they appear in IFC, matched by membership, carried on the method's component parameter declaration, as HDDL constrains a method's parameters rather than its state. A list because real models spell one material several ways. No material taxonomy, no subtype semantics, no kind constraint; if two kinds share a material and need different methods, add a slot then. Decided 2026-09-10; moved to the parameter 2026-09-17.
- `permanence` and `source` are required on every `BuildingComponent`, with no default. An unknown lifetime or provenance is a hole in the plan, and a default would silently mislabel temporary works. Confirmed 2026-09-10.
- Allocation is the `robot` parameter's binding on the `PrimitiveTaskInstance`, pointing at a machine node such as `sam100_2`; `assigned_unit` is retired. The planner binds the parameter through `requires` and `offers`; stage two may rewrite it with another machine of the same entry. A method's `robot` variable is bound once on the `CompoundTaskInstance` and its children inherit it. No mirror slot on `RobotUnit`; the reverse direction is a query. Decided 2026-09-10, target amended 2026-09-11, slot replaced 2026-09-17.
- `RobotType` is retired. The resource module is five classes: `RobotUnit` with `id`, `count`, and `status`, holding one object each of `PhysicalProperty`, `OperationalRequirement`, `Safety`, and `Activity`, each with its own authored `id` so it projects to a node. `offers` sits on `Activity`, where the paper's Task Type is, so `Activity` is the one required group. `status` is an enum, `idle`, `deployed`, `charging`, `out_of_service`, default `idle`. Decided 2026-09-11, see `robot-entry-as-type.md`.
- The rule table was amended 2026-09-12 from `docs/research/linkml-metamodel-conformance-and-inheritance.md`: identified objects project as nodes whether inlined or referenced; node ids are authored and edges have none; `ifabsent` defaults are the component's job; an edge class with an identifier or with a multivalued class-ranged slot is rejected. The same note fixes the inheritance policy: no `abstract`, `mixins`, or `union_of` in any module; `designates_type` only for `record_type`, which every product and process class carries with its value locked to the class name (product 2026-09-16, process 2026-09-17); `is_a` only in product, for kinds that need extra slots.
- `BuildingComponent` is subclassed by kind only, such as Wall or Brick, and only when a kind needs slots the others lack. Never by `source` or `permanence`: those are slots, because provenance and lifetime are facts about a component, not kinds of component, and a source-based class would change when the IFC model improves. `ifc_type` required for IFC-sourced components, and `derived_from` for derived ones, are class rules checked at tier 1; the GlobalId is the identifier itself, minted for derived records (2026-09-15). The one `is_a` so far is `Connector`, decided and named 2026-09-15 to cover doors, voids, and stairs, because a passage needs `connects` and clearances that no other component has; windows are components, not passages. Decided 2026-09-10.

- Process decisions of 2026-09-17, Phase 1 of SPEC-process, from `docs/research/pddl-for-process.md` and `docs/research/ma-pddl-for-process.md`: the ground classes are `PrimitiveTaskInstance` and `CompoundTaskInstance`. Parameter kinds are `component`, `location`, ranging over `Space` for now, and `robot`; `position` and `quantity` are gone, and the `ParameterKind` enum moves from common to process, its only reader. A method declares every variable its subtasks use, a superset of its task's parameters, as HDDL requires; tier 2 checks the declaration, the planner binds the variables the task does not hand down. Ground documents order only the parentless compounds; children inherit order and bindings from the method. Every process class carries `record_type`. HDDL export stays out of scope, but the catalogue is the domain, the product and resource documents are the problem, and the export writes the explicit labelled `:subtasks` and `:ordering` form, with ids `t1` to `tn` made from the positions. MA-PDDL is not adopted: a robot is a parameter, not an agent; per-agent goals, privacy, and concurrent-action formulas are not needed.

- Product decisions of 2026-09-14 and 2026-09-15, Phase 1 of SPEC-product, informed by `docs/research/ifc43-for-product.md` and `docs/research/topologicpy-for-product.md`: `material` optional, missing material a tier 3 work-list query. `target_location` required and a centroid; `supply_location` and `current_location` optional. `Storey` a class, so that "this storey contains these spaces and components" is two reverse queries; its GlobalId required because every storey comes from the parse. The exterior a derived Space per storey; `connects` exactly two. `name` and `long_name` optional everywhere. `contained_in` is IFC's containment relation and ranges Storey, reused for Space to Storey although IFC files that under aggregation; the component-to-Space relation is `located_in`. `derived_by` rejected; the producer of a derived component is not recorded. Stairs are Connectors of kind stair, joining two Spaces on different storeys; the subclass is named Connector rather than Opening for that reason. The product example documents are supplied by the author from a real model, not invented; the spec names the files and their invalid counterparts, the author fills them. Reviewed with SPEC-product the same day: `id` is the GlobalId, parsed or minted, and there is no separate `ifc_global_id`; `source` also on Space; `part_of` joins assembly parts to their assembly; windows are components, not Connectors; every model gets Spaces, derived from wall footprints when the file has none, so `connects` stays required and the exterior is one derived Space per storey.
